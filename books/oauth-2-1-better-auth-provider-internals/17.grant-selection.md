## flow chartより先に聞くこと

Grant選定で最初に聞くのは「どのライブラリが簡単か」ではありません。

1. TokenのprincipalはResource OwnerかClient自身か
2. ClientはBrowser redirectを扱えるか
3. Client Secretやprivate keyを安全に保持できるか
4. 利用者がその端末でAS画面を操作できるか
5. 継続アクセスが必要か

この答えから候補を絞ります。

| Grant | principal | Client例 | secret | user interaction |
| --- | --- | --- | --- | --- |
| Authorization Code + PKCE | user | React SPA | 不要 | Browser redirect |
| Refresh Token | 既存grantを継続 | React / BFF | Client型による | 通常は再Consentなし |
| Client Credentials | client | Indexer job | 必要 | なし |
| Device Authorization | user | CLI / TV | Publicなら不要 | 別Browser |

## 選ばないgrant

Implicit GrantはAccess TokenをAuthorization responseへ直接返し、Browser URL周辺へ漏れる面が大きいため使いません。Authorization Code + PKCEで置き換えます。

Resource Owner Password Credentials GrantはClientがpasswordを収集するため使いません。ASの認証policyやMFAを迂回します。

Client Credentialsを「ユーザー操作のない万能flow」としてuser dataへ使うことも避けます。user consentやsubjectを表現できないためです。

## 同じToken endpointで責務を揃える

4つのGrantは同じToken endpointへ入りますが、入力と検証が違います。Better AuthのToken処理は`grant_type`でhandlerを分ける前にClient認証を解決し、登録済みGrantかを確認します。

その後、grantごとのcredentialを検証します。

- Code: code + redirect URI + PKCE
- Refresh: refresh token + family + scope/resource narrowing
- Client Credentials: authenticated client + scope ceiling
- Device: device code + approval state + polling policy

共通endpointだから共通のcredentialを使うわけではありません。

## checkpointで確認する

Part 3終了時点で次を観測できれば、Grantを単なるURL暗記から切り離せています。

- Refresh後にAccess/Refresh Token両方のfingerprintが変わる
- 古いRefresh Tokenが拒否される
- JWTの`aud`がNotes APIで、別audienceでは拒否される
- Indexer Tokenにuser `sub`を捏造できない
- Device CLIが`slow_down`を受けてintervalを増やす
