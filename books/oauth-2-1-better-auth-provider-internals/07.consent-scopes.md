## Clientを信頼する画面ではない

Consentは「このアプリを信頼しますか」という曖昧な確認ではありません。Client、Resource、要求scope、既存grantとの差分をResource Ownerへ示し、今回委譲する集合を確定する操作です。

ASが持つscope catalogは次の情報を返します。

```ts
{
  name: 'notes:write',
  label: 'ノートを編集',
  description: '新しいノートを作成し、既存ノートを更新します',
  risk: 'high'
}
```

Clientがquery parameterでlabelを送る構成にすると、`notes:write`を「表示設定」などと偽装できます。scope identifierと説明の対応はASが所有します。

## requiredとoptionalを分ける

Provider clientの`consent` APIから、要求scopeと選択可能性を受け取ります。UIはrequired scopeを外せないようにし、optional scopeだけcheckboxで選べるようにします。

```ts
await authClient.oauth2.consent({
  accept: true,
  scope: [...selectedScopes].join(' '),
  oauth_query: oauthQuery
})
```

拒否を選んだ場合は`access_denied`をClientの検証済みRedirect URIへ返します。Client側はこれをnetwork errorとして扱わず、Resource Ownerが認可しなかった結果として表示します。

## Consent recordの意味

`oauth_consent`はuserとclientの組に対する承認scopeを保持します。Access Tokenそのものではありません。Tokenを失効させても、同じscopeの再認可でConsent画面を省略できる場合があります。逆にConsentを削除しても、すでに発行済みTokenの状態を別途扱う必要があります。

ここから次の3つを分けられます。

- **authorization decision**: 何を許可したか
- **credential**: その決定を提示するAccess Token
- **session**: Resource OwnerがASへログイン中か

## step-upを観測する

最初に`notes:read`だけを認可します。後で「ノート作成」を選んだとき、新しいAuthorization Requestに`notes:write`を加えます。

ASは以前のConsentがあるからといって、新しいscopeを黙って追加しません。差分の`notes:write`を確認させ、更新されたConsentを保存します。Client側のbuttonをdisabledにするだけでは権限制御にならないため、RSも`notes:write`を検証します。

## scope名の設計

`read`のような短い名前は別Resourceと衝突します。ラボは`notes:read`、`notes:write`、`notes:index`とdomainを含めます。`notes:index`はResource Ownerのdelegated scopeではなく、Indexer Clientだけに許すClient Credentials scopeです。

OIDCの`openid`、`profile`、`email`、`offline_access`はPart 4で意味を追加します。今は同じspace-separated文字列に見えても、scopeごとに発行物とpolicyが違うことだけ覚えておいてください。
