## 一度使ったRefresh Tokenを捨てる

Public ClientのRefresh Tokenはsender-constrainedではありません。盗まれた値を攻撃者も使えるため、[RFC 9700](https://www.rfc-editor.org/rfc/rfc9700)はpublic clientに対してrotationまたはsender constraintを要求します。

ラボは`refreshTokenReuseInterval: 0`を設定し、猶予を設けないstrict rotationから始めます。

```text
RT-1 ──exchange──> AT-2 + RT-2
RT-1 ──reuse─────> invalid_grant
RT-2 ──exchange──> AT-3 + RT-3
```

## Client側のatomic update

Token Responseを受け取ったら、Access TokenだけでなくRefresh Tokenも一つのToken Setとして置き換えます。

```ts
const next = await readOAuthResponse(response)
setTokens(next)
```

新しいAccess Tokenを保存した後で古いRefresh Tokenが残る、といった部分更新を避けます。ラボのPublic Clientはmemory stateなので一回のstate updateで交換します。BFFへrefreshを追加する場合は、永続DBのtransaction内で暗号化Token Setを更新します。

## retryが危険になる理由

network timeout時、ClientはASがrequestを受理したか分かりません。同じRefresh Tokenを自動retryすると、最初のrequestが成功していた場合にreuseになります。

短いreuse intervalを設けて同時requestを吸収する実装もありますが、攻撃検知の感度とのtrade-offです。本書は既定の0秒を明示し、Client側でrefreshをsingle-flightにする設計を優先します。

## family invalidationを考える

古いRefresh Tokenが再利用されたとき、単にその一件を拒否するだけでは、攻撃者がすでに新しいTokenを得ている可能性があります。Token family全体を無効化し、利用者へ再認証を求めるのが強い対応です。

Better Authのversionでどこまでfamily revocationされるかは、sourceとintegration testを固定して確認します。「rotation有効」という設定名だけから挙動を推測しません。

## 自動化したreuse testと、追加すべきrace test

ラボのBrowser E2Eは、一度refreshして新しいToken Setを得た後、交換前のRefresh Tokenを再送し、`invalid_grant`になることを確認します。これにより逐次的なreuse拒否までは継続検証できます。

一方、同じRefresh Tokenで2 requestをほぼ同時に送るraceは、DB統合テストとして別に追加すべきcheckpointです。期待する結果は成功が最大1件で、残りは失敗です。さらにDBで後継Tokenが複数生成されていないことを確認します。本書はこの同時実行テストを実装済みとは扱いません。

Client側でもbutton連打や複数tabが同時refreshしないようにします。Browser memoryをtab間共有しない設計なら、それぞれが別認可transactionを持つ方が単純です。

## Inspectorでrotationを見る

画面には生Tokenを出さず、交換前後のSHA-256 fingerprintが変わったことを表示します。古い値を再送するnegative testはtest code内だけで行い、artifactへTokenを保存しません。
