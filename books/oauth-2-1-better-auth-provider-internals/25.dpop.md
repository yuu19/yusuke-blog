## Bearer Tokenの弱点

Bearer Tokenは「持っている者」が使えます。TLSで通信中の盗聴は防げても、Client storage、log、extension、proxyから漏れたTokenを別processがreplayできます。

[RFC 9449](https://www.rfc-editor.org/rfc/rfc9449)のDPoPはAccess TokenをClientのpublic key thumbprintへ結び付け、requestごとにprivate keyでproof JWTを作ります。

![DPoP-bound Tokenの発行とAPI request](/images/books/oauth-2-1-better-auth-provider-internals/dpop-protocol.png)

## proofのclaim

```ts
new SignJWT({
  htm: request.method,
  htu: new URL(request.url).href,
  iat: Math.floor(Date.now() / 1000),
  jti: crypto.randomUUID(),
  ath: base64url(sha256(accessToken)),
  nonce
}).setProtectedHeader({
  typ: 'dpop+jwt',
  alg: 'ES256',
  jwk: publicJwk
})
```

Token endpointでのproofには通常`ath`がなく、発行されたTokenには`cnf.jkt`が入ります。RS requestでは`ath`がAccess Tokenをproofへ結び付けます。

```text
Authorization: DPoP <access-token>
DPoP: <proof-jwt>
```

## RSが検証する順序

1. `typ`と許可algorithm
2. embedded public JWKと`cnf.jkt`
3. signature
4. `htm`が実request methodと一致
5. `htu`がfragmentなしの実request URLと一致
6. `iat`が許容時間内
7. `jti`が未使用
8. `ath`がAccess Token hashと一致
9. serverが要求したnonce

![Better Auth verifyAccessTokenRequestのDPoP検証境界](/images/books/oauth-2-1-better-auth-provider-internals/dpop-provider-db.png)

Better Auth 1.7.1の`verifyAccessTokenRequest`はBearer/DPoPをrequest単位で検証します。DPoP-bound Tokenを生Token verifierへ渡してBearerとして通さないことが重要です。

## replay storeはdatabase-backedにする

`jti` replayをprocess memoryだけで記録すると、複数instanceの別nodeへ同じproofを送れます。Providerはverification storeをDB-backedにし、instance間でone-timeを共有します。secondary-storageだけで安全性を満たせない構成では、DPoPを黙って弱めずrequestを拒否します。

## nonce retry

ASやRSが`DPoP-Nonce`を返した場合、Clientは同じproofを再送せず、新しい`jti`・`iat`と受け取ったnonceでproofを作り直します。Access Tokenは同じでもproofはrequestごとに新しいものです。

## 限界

DPoPはClient process内でprivate keyを使えるXSSまで防ぎません。keyをnon-extractableにしても、悪意あるscriptが署名operationを呼べる場合があります。BFFやOS key storeと組み合わせる方が境界を強くできます。
