## Authorization Requestを先に押し込む

[RFC 9126](https://www.rfc-editor.org/rfc/rfc9126)のPushed Authorization Requests（PAR）では、Clientが認可parameterをASのback-channel endpointへ先にPOSTします。ASは短寿命の`request_uri`を返し、Browser front-channelにはその参照だけを載せます。

```text
POST /par  -- authenticated client + authorization parameters --> AS
          <-- request_uri=urn:ietf:params:oauth:request_uri:... --

GET /authorize?client_id=...&request_uri=...
```

長いclaim requestをURLへ出さず、Client認証後にparameterを固定できる利点があります。

## Better Auth 1.7.1が提供する境界

OAuth Providerには`requestUriResolver` optionがあります。

```ts
requestUriResolver: async ({ requestUri, clientId, ctx }) => {
  const stored = await parStore.consume(requestUri)
  if (!stored || stored.clientId !== clientId || stored.expiresAt < new Date()) {
    return null
  }
  return stored.parameters
}
```

Authorize endpointが`request_uri`を受けると、まずURL上の`client_id`を要求し、resolverへ渡します。resolverが返した保存済みparameterでquery全体を置き換え、URL上の他parameterを混ぜません。RFC 9126のparameter integrityを守る重要な実装です。

## 本書でendpointを自作しない理由

Providerはresolver boundaryを提供しますが、完全なPAR endpoint、Client認証、request保存、one-time consume、expiry、metadata公開を自動で構築するわけではありません。

学習用に不完全な`/par`を数行で足すと、次を落としやすくなります。

- Client認証方式の統一
- Redirect URIとscope/resource validation
- Request Objectとの競合
- 推測不能な`request_uri`
- 一回限りのconsume
- 短いexpiryとcleanup
- rate limitとaudit
- `pushed_authorization_request_endpoint` metadata

そのためラボではPAR endpointを提供せず、discoveryも`request_uri_parameter_supported: false`のままです。章ではresolverの接続点と、実装に必要なcontractを示すところまでに限定します。

## errorの境界

- resolver未設定で`request_uri` → `request_uri_not_supported`
- `client_id`なし → `invalid_request`
- unknown/expired/consumed URI → `invalid_request_uri`
- `request`と`request_uri`を同時送信 → `invalid_request`

「未実装」を正常系fallbackにせず、明示的errorにすることが相互運用性を守ります。
