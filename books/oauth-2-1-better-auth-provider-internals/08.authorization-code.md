## callbackへ戻る値

Consentが確定すると、ASは登録済みRedirect URIへ次のparameterを付けて戻します。

```text
HTTP/1.1 302 Found
Location: http://127.0.0.1:4200/callback?
  code=...&
  state=...&
  iss=http%3A%2F%2Flocalhost%3A4100%2Fapi%2Fauth
```

Codeの中身をClientが解釈する必要はありません。短時間だけ有効で、一度Token endpointへ提示したら消費される引換券です。

## Codeへ結び付くもの

`oauth_authorization_code` recordには少なくとも次の関係が必要です。

- 発行先`client_id`
- 正確な`redirect_uri`
- 許可されたscope
- Resource OwnerとAS session
- PKCE `code_challenge`とmethod
- resource indicator
- 有効期限と消費状態

Codeだけを盗んでも、別Client、別Redirect URI、PKCE verifierなしではTokenへ交換できない構造です。

## callbackで先に検証する順序

ClientはCode交換より先に`state`と`iss`を検証します。

```ts
const transaction = consumeTransaction(sessionStorage, returnedState)
assertIssuer(query.get('iss'), transaction.issuer)
```

`consumeTransaction`は読んでから消すのではなく、lookup keyとrecordを直ちに削除してから内容を検証します。例外が起きても同じcallbackを再利用できません。

`iss`は[RFC 9207](https://www.rfc-editor.org/rfc/rfc9207)のAuthorization Server Issuer Identificationです。複数ASを扱うClientでresponse mix-upを防ぎます。ラボは一つのASしか使いませんが、設計を単一環境の偶然へ依存させません。

## Codeを画面へ残さない

Token交換が完了したら次を実行します。

```ts
history.replaceState(null, '', '/')
```

これによりBrowser history、copyしたURL、screenshotへCodeを残しません。Codeは短命・一回限りでもcredentialです。

## failureを観測する

- 同じcallback URLを再読込 → transactionが消費済みで拒否
- `state`を1文字変更 → unknown state
- `iss`を別originへ変更 → issuer mismatch
- 期限を10分進める → transaction expired
- Codeを別Client IDで交換 → `invalid_grant`

Authorization CodeはAccess TokenをURLへ載せないための中間物ですが、Code単体の秘匿性だけには頼りません。次章でPKCE verifierを提示し、開始したClient instanceとの結び付きを完成させます。
